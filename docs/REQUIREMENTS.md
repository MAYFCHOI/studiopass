# 학원 출결·정산 관리 — 요구사항 정리 (v0, 2026-10-10)

원문: 의뢰인이 보낸 초기 요구사항 4개 묶음(회원관리 / 결제 입금 처리 / 정산 정리 / 전문반 특수 케이스).
의뢰인 측 키오스크 업체 답변: "앱/웹 시스템으로 관리 가능, 원하는 정보만 선택해서 엑셀로 추출 가능". API 제공 여부는 미답.

## 1. 기능 요구사항 분해

### 1.1 회원 (Member)
| ID | 요구 | 비고 |
|---|---|---|
| M1 | 회원 등록: 이름, 연락처, 회원번호(자동 발번) | 연락처 = 키오스크 결제자 매칭 키 |
| M2 | 회원별 QR 발급 | QR 안에는 **회원 식별자만** 담는다(개인정보·수업·회차는 서버 조회). 이름/연락처를 QR 에 넣으면 유출·위변조 위험 |
| M3 | QR 전달: 화면 표시 + 이미지 저장 + 카톡 전송(수동) | 인쇄 카드 옵션 |
| M4 | 회원 상세: 보유 수강권(수업, 잔여 회차, 유효기간), 출석 이력, 결제 이력 | |

### 1.2 수강권 (Pass)
| ID | 요구 | 비고 |
|---|---|---|
| P1 | 회차권: 수업 + 총 회차 + 잔여 회차 + 유효기간 | 일반반 |
| P2 | 기간권(전문반): 결제일 기준 1개월 유효 + 월 N회 자유수강 티켓 | 월 경계·연장 규칙 확정 필요 |
| P3 | 결제 1건 → 수강권 1건 생성(또는 기존 수강권 회차 추가) | 결제-수강권 매핑 규칙 |

### 1.3 출석 (Attendance)
| ID | 요구 | 비고 |
|---|---|---|
| A1 | 카메라로 QR 스캔 → 회원 식별 → 오늘 시간표에서 수업 선택(또는 자동) → 출석 기록 + 회차 차감 | 스캐너 = 폰/태블릿 브라우저 |
| A2 | 전문반 출석: 자유수강 티켓 1장 차감, **어느 강사 수업인지** 기록 | 정산 입력값 |
| A3 | 중복 스캔 방지(같은 수업 1회), 잔여 0 / 기간 만료 시 경고 | |
| A4 | 출석 취소·수정(관리자) | 감사 로그 |

### 1.4 결제 (Payment)
| ID | 요구 | 비고 |
|---|---|---|
| Y1 | 키오스크 결제 내역 가져오기 | §3 연동 전략 3단계 |
| Y2 | 결제자 특정: 휴대폰 번호 → 회원 매칭. 미매칭은 "미배정" 큐에 두고 수동 배정 | 번호 포맷 정규화 |
| Y3 | 결제 → 수강권 생성 규칙(상품명 ↔ 수업/회차 매핑 테이블) | 키오스크 상품명이 키 |
| Y4 | 수동 결제 입력(현금, 계좌이체) | 키오스크 외 결제 |
| Y5 | 취소/환불 반영 → 수강권 회수 | |

### 1.5 정산 (Settlement)
| ID | 요구 | 비고 |
|---|---|---|
| S1 | 강사별 정산 규칙 설정 | 유형 1 비율제(학원:강사 = a:b), 유형 2 타임제(1타임당 x원, 결제액은 전액 학원 귀속) |
| S2 | 월별 정산표 자동 생성, 강사별 정렬/필터 | 산출 근거(출석·결제 건) 추적 가능하게 |
| S3 | 전문반 정산: 자유수강 티켓 출석을 강사별 집계 | 월정액을 강사별로 어떻게 배분하는지 **규칙 확정 필요** |
| S4 | 엑셀 내보내기 | 의뢰인 기존 습관이 엑셀 |

### 1.6 미확정 질문 (의뢰인에게)
1. 비율제의 "결제액" 기준: 결제 시점 금액인가, 출석 1회당 환산 금액(결제액/회차)인가? 환불 시 소급?
2. 타임제: "1타임" 정의(수업 1회? 시간 단위?). 수강생 0명 수업도 지급?
3. 전문반 월정액 정산: 강사별 분배 규칙이 있나(출석 횟수 비례? 고정?). 아니면 정산 대상 아니고 기록만?
4. 전문반 유효기간: 결제일 +1개월 vs 달력 월. 미사용 티켓 이월 여부.
5. 한 회원이 여러 수강권 보유 시 차감 우선순위.
6. 사용자: 관리자 1명 + 강사가 스캐너를 쓰는가(강사 로그인 필요?).
7. 지점 수(1개?), 동시 사용 기기 수, 회원 규모(백 단위?).
8. 키오스크 업체명·모델, 관리 웹에서 뽑히는 엑셀 컬럼 샘플(마스킹해서).

## 2. 도메인 모델 (초안)

```
Member(id, member_no, name, phone, created_at)
Instructor(id, name, settlement_type[RATIO|PER_SESSION], ratio_academy, ratio_instructor, per_session_fee)
Course(id, name, instructor_id, kind[GENERAL|PRO], default_sessions, price)
Schedule(id, course_id, weekday, start_time, end_time)
Payment(id, source[KIOSK|MANUAL], external_id, paid_at, amount, payer_phone, product_name, status[APPROVED|CANCELLED], member_id?, raw_json)
Pass(id, member_id, course_id?, kind[COUNT|PERIOD], total_count, remaining_count, valid_from, valid_to, payment_id)
Attendance(id, member_id, pass_id, course_id, instructor_id, attended_at, scanned_by, cancelled_at?)
SettlementRun(id, year_month, generated_at) / SettlementLine(run_id, instructor_id, basis, amount, detail_json)
ProductMapping(product_name_pattern -> course_id, kind, count, period_days)
```

QR payload: `AM1:<member_id>:<hmac8>` (서명 짧게 붙여 임의 생성 방지).

## 3. 키오스크 연동 전략 (조사 결과 반영)

조사 결론(2026-10-10): 국내 키오스크/POS 업체는 **공개 API 가 일반적이지 않다.** 예외는 토스플레이스(Open API + 웹훅, 결제 객체에 결제자 식별은 없고 `cashReceipt.identityNumber` 가 마스킹된 휴대폰 번호). 학원 전용 키오스크(메이크에듀, 클래스업 등)는 자사 관리 솔루션 안에서만 연동. 페이히어·포스뱅크·KICC·KSNET 은 공개 문서 없음(제휴 문의 필요). 업체 답변 "웹에서 엑셀 추출"은 **엑셀이 유일하게 보장된 경로**라는 뜻으로 본다.

| 단계 | 방식 | 조건 | 비고 |
|---|---|---|---|
| T1 (기본, 반드시) | 엑셀/CSV 업로드 → 파싱 → Payment 적재(중복은 external_id 또는 승인번호+시각으로 멱등) | 업체 관리 웹에서 사람이 내려받음 | 1일 1회 수작업. 컬럼 매핑 UI 로 업체 포맷 변경 흡수 |
| T2 (있으면) | 업체 API 폴링(결제 목록 조회) | 업체가 API 키 발급 | T1 과 같은 적재 경로 재사용 |
| T3 (최상) | 웹훅 수신 | 업체가 웹훅 지원(토스플레이스 등) | 공개 HTTPS 엔드포인트 필요 |

→ 적재 로직을 `PaymentImporter` 인터페이스 하나로 두고 T1/T2/T3 를 어댑터로. 핵심은 **결제자 휴대폰 번호가 추출 데이터에 포함되는지**. 없으면 매칭이 불가능하므로 업체에 최우선 확인.

### 업체에 물을 것 (의뢰인 통해)
1. 결제 내역에 결제자 휴대폰 번호(또는 회원 식별값)가 포함되는가. 마스킹 여부(뒤 4자리만이면 매칭 정확도 낮음).
2. 엑셀 추출 컬럼 목록과 샘플 1건. 결제 취소 건의 표기 방식.
3. 외부 연동 API 또는 웹훅 제공 여부, 제공 조건(제휴·비용).
4. 키오스크 상품(메뉴) 이름을 우리가 정할 수 있는가(상품명 ↔ 수업 매핑 키로 쓰기 위해).

## 4. MVP 범위 제안
1. 회원·수업·강사 CRUD, QR 발급
2. QR 스캔 출석 + 회차 차감(일반반), 전문반 티켓 차감 + 강사 기록
3. 엑셀 업로드 결제 적재 + 휴대폰 매칭 + 미배정 큐
4. 월 정산표(비율제·타임제) + 엑셀 내보내기
보류: 웹훅, 강사 로그인, 문자 발송, 멀티 지점.

## 5. 기술 선택 (제안, 사용자 결정 대기)
- 형태: 모바일 우선 웹앱(PWA). QR 스캔은 브라우저 `BarcodeDetector` + 폴백(zxing-js). 앱스토어 배포 불필요.
- 스택 후보 A: Next.js + Postgres(Supabase: Auth·DB·Storage 무료 티어) — 호스팅 Vercel. 서버 관리 0.
- 스택 후보 B: FastAPI/SQLite 단일 서버 + 정적 프론트 — 소형 VPS 1대, 백업 단순, 비용 ₩5천/월대.
- 엑셀: SheetJS(읽기) / exceljs(쓰기).
- 의뢰인 데이터는 개인정보(이름·연락처). 전송 TLS, 저장 시 연락처 최소 수집, 접근은 로그인 필수.

## 키오스크 업체 확정: 오케이포스(OKPOS) (2026-10-11 조사)

- NICE 그룹 계열 POS/키오스크. 공개 개발자 API 없음. 외부 연동(오늘얼마, 채널톡 등)은 제휴 방식으로 ASP 데이터에 붙는 구조.
- 결제 내역 경로: 영업정보시스템 ASP(asp.netusys.com, IE/Edge+플러그인, 크롬 불가) → 매출관리 > 매출현황 > 당일매출상세현황 → 엑셀 다운로드(엑셀 설치된 PC). 모바일은 "오늘얼마" 앱(영수증에 회원명·포인트 표시, 내보내기 언급 없음). MY OKPOS 는 신형 웹 관리(상품·매장 설정, 채널별 통계).
- **결제자 전화번호는 기본 기능이 아니다.** 키오스크 포인트/스탬프 적립은 "기본 기능 아님, 단골플러스 서비스 신청 시 가능"(뉴 키오스크 FAQ). 전화번호 매칭을 하려면 단골플러스 가입 + 회원이 결제 때 번호 입력이 전제. 엑셀에 번호가 찍히는지는 미확인.
- 대안: 번호가 없으면 "확인 필요" 큐에서 이름·시각·승인번호로 수동 연결(현재 구현). 승인번호는 영수증에 있으니 회원이 영수증을 보여주면 연결 가능.
- 업체/대리점에 물을 것: ① 당일매출상세현황 엑셀 샘플 1부(컬럼) ② 단골플러스 쓰면 엑셀에 전화번호가 나오는지 ③ 상품명이 등록한 수강권 이름 그대로인지 ④ 취소/환불 표기 방식 ⑤ 점주 PC 에서 ASP 접속 가능 여부 ⑥ 제휴 API 가능 여부(기대 낮음).
